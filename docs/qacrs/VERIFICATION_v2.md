## 2. What the v1 percentages actually measure

| Name in v1 | Exact meaning | What it is NOT |
|---|---|---|
| `p_best` (e.g. 26.9%, 96.5%) | probability that ONE measurement returns an optimal decision of that scenario's QUBO | not detection accuracy, not a success rate of the defence |
| "found in 100 shots" (31/38) | number of scenarios where 1−(1−p_best)^100 > 0.99, computed **analytically** from the state vector | not 100 real samples drawn |
| `random` (3.3%) | share of all 2^n decisions that are optimal (blind guessing) | not a classical baseline solver; simulated annealing and brute force find the optimum 40/40 |
| `ratio` | (worst − mean cost) / (worst − best) of the measured distribution | — |

Also found: in 14/38 scenarios a deeper circuit (higher p) gave a LOWER p_best than a shallower one, so "more depth is better" is not guaranteed with this optimiser. On the hard scenarios CVaR raises the chance of the optimum but lowers the average quality (ratio 0.947 → 0.896); this is the expected CVaR trade-off and must be stated with the result.

**Result: H1 NOT SUPPORTED as written.** Honest note: the pre-registration has an internal inconsistency. Its hypothesis sentence includes "isolates fewer healthy machines", but its rejection rule names only containment (80%) and services down. The code applies the stricter sentence. ### Where Q-ACRS fails, and why

- **4 of 8 failures: a hacked critical server (database or domain controller) with risk ≥ 7 is only restricted.** In the QUBO, isolating the database or the domain controller takes down the services that need it, which outweighs its leftover risk, so the optimum never isolates it. This is a real weakness of the weights, not a solver error: `net12_h04` {'db': 8}, `net12_h06` {'pc_admin': 8, 'dc': 7}, `net12_r03` {'pc_nurse': 4, 'web1': 5, 'db': 7}, `net12_r07` {'app1': 4, 'db': 8, 'lab': 5, 'web2': 9}.
- **4 failures are shared with safe full isolation:** a hacked device that may never be isolated (lab analyzer) has a link to the database. No method closes that path without isolating a healthy critical server. These are structural limits of the scenario, flagged for the device owner.
- Q-ACRS never produced an unsafe decision and never isolated a healthy machine in this run.

**Proposed v3 change (to be pre-registered, not applied here):** when a critical server is hacked with risk ≥ 7, the system must output `HUMAN_APPROVAL_REQUIRED` (two-person rule) instead of silently restricting it. This turns the 4 silent failures into explicit escalations.

## 4. Mathematical checks (automated tests)

`cd backend && python -m unittest tests.test_qacrs -v` checks, among others:

- the BIG penalty: in every scenario where a never-isolate device is a variable, every decision that isolates it costs more than the most expensive decision without it, so weights can never outvote this rule;
- problem reduction: on the 12-machine network the reduced QUBO has exactly the same optimum as the full 12-variable QUBO in all 20 scenarios;
- QUBO ↔ Ising conversion is exact; vectorised and scalar cost agree; simulated annealing reaches the exact optimum in 40/40;
- the safety layer rejects never-isolate devices, unknown machines, invalid risks, empty or wrong-network scenarios; critical servers need two people;
- the summary in `containment.json` is recomputed from its raw rows, and no failure is counted as a success.
