# ACRS — Pre-registration v11: real incidents 2016–2026, replayed on the unchanged engine

**Written:** 2026-10-18, **before any incident was converted and before any v11 result was computed.** Committed alone,
with no code and no data. Drafted with Claude (Anthropic) at the student's request; the student approved the rules.
The v9 engine is used **unchanged**: no weight, threshold, rule or solver setting is modified. The 11 files locked for the
blind test (`LOCK_blind_v9.json`) are not touched.

## Why

Every ACRS result so far comes from synthetic attack chains generated by code the student wrote. The strongest answer to
"you wrote the exam and then passed it" is to replay **attacks that really happened**, documented by third parties
(CISA, NCSC, NAO, vendor incident reports), on networks rebuilt **from those public reports**, with the engine frozen.

The decade **2016–2026** is chosen so that the set spans attacks that predate the project (WannaCry 2017 is the incident
that motivated Section 2 of the Ibdaa form) and attacks that **post-date the engine's design** (2025–2026), which the
engine could not have been tuned for.

### Conversion rules (mechanical; the converter does not see engine output)

A conversion is a text file per incident, filled by **a person other than the student** (the "converter"), from the
public sources only. The student then runs it once. Rules:

1. **Machines.** Every host, server or system *named or clearly implied* in the report becomes one machine. Generic
   groups ("hundreds of workstations") become **at most 10** machines of that type. Roles are copied from the report
   (e.g. "pathology LIMS server", "SWIFT Alliance Access server", "domain controller").
2. **Never-isolate and critical flags.** A machine is `never-isolate` only if the report says disconnecting it endangers
   life or physical safety (medical devices, safety instrumented systems). A machine is `critical` if the report says
   its loss stops a core service (domain controller, core banking DB, LIMS, billing). Everything else is a plain machine.
3. **Services.** Every business service the report says was **disrupted or at risk** becomes one service, with the
   machines the report attributes it to. A service has two machines (a "twin") only if the report says there was
   redundancy; otherwise one.
4. **Links.** One link per lateral movement the report describes (A → B). Plus: every workstation links to the domain
   controller and file server if the report mentions domain credentials being used. No other links are invented.
5. **Hacked machines (the alert set).** The machines the report says were compromised **at the moment the defenders
   first detected the attack**, or, if that moment is not stated, at the moment the attack was first publicly known.
   Later-stage encryption of everything is **not** the alert set (that is the outcome ACRS is meant to prevent).
6. **Leftover risk (1–10)** from the ATT&CK technique the report attributes to that machine, by this fixed table:
   ransomware deployment / wiper on the host (T1486, T1485) = 9; domain-admin credential theft or Kerberoasting
   (T1003, T1558) = 8; active C2 beacon (T1071, T1219) = 7; lateral movement tool present (T1021, PsExec, AnyDesk) = 6;
   initial access only, no confirmed post-exploitation (T1190, T1566, T1133) = 5. If several apply, take the highest.
7. **Weights** stay the engine's existing 1–10 design scale. The converter sets `d` (disruption cost) from the report:
   life-critical = 5, core business = 3–4, support = 2, workstation = 1.
8. **Ambiguity** is logged in the conversion file, not resolved by guessing: if the report does not say, the field is
   left at the plain default.

### Engine, baselines, metrics (identical to v9/v10)

ACRS v9 portfolio (`hassan.solve` + `qubo_v7.decide_v7`), exactly as in `phase14_v9.py`. Baseline = safe full isolation
(`qubo_v7.m_full_isolation_safe`). Metrics: containment status, services down (ACRS vs baseline), unsafe decisions,
silent failures, escalations to humans, decision time. Each incident is one scenario; where a report describes
**several detection moments**, each becomes a separate scenario (expected total: 10–20 scenarios).

### Targets

| ID | Target |
|---|---|
| R1 | **0** unsafe decisions and **0** silent failures across all converted incidents |
| R2 | In every incident where the baseline (full isolation) takes ≥ 1 service down, ACRS takes **fewer** services down |
| R3 | ACRS reaches CONTAINED or PENDING (human approval) in ≥ 80% of scenarios |

Because the sample is small (10–20 scenarios), R2 and R3 are reported as counts with Wilson 95% intervals, **not** as a
hypothesis test; no p-value is claimed. Every miss is published with the incident name and the reason.

### What this experiment does and does not show

- It shows whether a frozen engine, tuned only on synthetic hospital data, behaves safely on **real attack paths** from a
  decade of incidents, including ones that happened after the engine was designed.
- It does **not** show that ACRS would have stopped these attacks in reality: the internal network diagrams of the victims
  are confidential, so the networks here are partial reconstructions from public reports, and detection is assumed at the
  moment the report describes. This limitation is stated in every table and in the form.

### Procedure and honesty controls

1. This file is committed alone (commit hash recorded in RESULTS_v11.md).
2. The converter receives this file and the public sources; **not** the engine, **not** the results of any earlier
   experiment, and **not** the student's networks.
3. Conversion files are committed by the converter (or by the student unchanged, with the converter named in the
   commit message and a signed note in `docs/qacrs/v11_converter_statement.md`).
4. `phase16_v11.py` is written **after** the conversions are committed and does nothing but load them, run the engine once,
   and write `results/v11/v11.json`. Its hash is recorded.
5. Results are published whatever they are.
